# c82 — Refund unearned trust money when a matter ends

Status: draft product spec. Not legal or accounting advice; builds on the
attorney+CPA-reviewed `docs/compliance/trust-accounting-iolta-compliance-review.md`
(c75) and the shipped ledger/reconciliation code (c76), and does not revisit
either's conclusions.

## Trigger

Fires whenever a matter is closing — either the firm closes it in the
ordinary course, or the client ends the relationship early (the card note
calls out both). Either path runs the same close-out sequence below; nothing
in this spec distinguishes "fired" from "finished" representation, because
the trust math is identical — only the engagement-letter/liability question
differs, and that's a separate (legal, not product) concern for the lawyer.

## What the system works out

At close, read the matter's trust ledger (c76) and:

1. Sum everything still held in trust for this client on this matter.
2. Of that, work out what's **earned** (billed and paid per the earning
   schedule from c52, or time-and-expense entries approved but not yet
   invoiced — those get a final invoice first, see below) versus
   **unearned** (fixed-fee money never reached an earning milestone, or an
   unapplied retainer balance above $0).
3. Anything earned but not yet invoiced becomes a **final invoice**,
   generated the same lawyer-reviewed-draft way every other invoice is
   (c79 — reusing that flow, not building a second one).
4. Anything unearned becomes a **refund** for the lawyer to approve — this
   spec never auto-sends client money. A lawyer must explicitly approve
   the refund amount (which can be the system's computed figure or a
   corrected one, with the correction reasoned and audited) before it
   disburses.

## The hold: closing is blocked, not silently allowed, until trust is clean

The matter **cannot be marked closed** while its client-matter trust balance
is nonzero, unless a lawyer has recorded, in writing, why money is being
held — the card note's own example is a disputed amount, which the
existing "disputed amounts stay in trust until resolved" hard rule (restated
in c50/c52) already anticipates. This is implemented as a precondition check
on the close-matter action, not a warning the lawyer can click past: if the
balance isn't zero and no hold reason is on file, the close attempt is
refused with the actual balance and the two ways to proceed (approve the
refund, or record a hold reason).

A hold reason doesn't close the ledger entry — the matter can still show as
"closed" in every other sense (no more time entries, no more new
correspondence) while the trust sub-ledger for that client stays open until
the held amount is resolved. Resolving it later re-enters this same
close-out sequence for just the trust portion.

## Approval and audit

The refund itself is a trust disbursement — same as every other movement of
trust money — so it goes through
`requireApproval("rules.trust_accounting", { action: "billing-trust.matter_close_refund", tenantId })`
before it posts (reusing `RULE_GATES.trustAccounting`, which already lists
c82 in its `cardIds`). The lawyer's approval of the computed amount (or their
correction, with reason) is a second, separate record — a human sign-off on
*this specific number*, distinct from the standing attorney+CPA sign-off on
the *rule* that governs trust money generally. Both get an audit row (c6):
`trust.matter_close_computed` when the system works out the split, and
`trust.matter_close_refund_approved` when the lawyer signs off.

## The refund letter

A plain-language letter accompanies the refund (and, where relevant, the
final invoice): what was held, what was earned and billed, what's being
returned, and how. This is generated by the Document engine (c39-style
template fill, not a new letter-generation mechanism) — billing-trust hands
off the computed numbers via a `tasks` row
(`kind: "document.generate_matter_close_letter"`, per the
cross-engine-cooperation rule in `src/engines/README.md`: engines talk
through shared tables, never by importing each other) rather than calling
into the document engine directly.

## What this spec deliberately does not do

- It does not decide what happens to the *representation* itself (withdrawal
  procedure, final correspondence content) — that's the lawyer's call,
  same boundary as c50/c52.
- It does not change how disputes are flagged or resolved — it only honors
  an existing hold the lawyer has already recorded.
- It does not refund card-processing fees or decide who absorbs them —
  that's a vendor-contract question for whoever picks the payment processor
  (c80).

## Data model note (no migration in this PR)

No new top-level table; this adds a `closeHoldReason` / `closeHoldSetAt` /
`closeHoldSetByUserId` column set to the matter record (or an equivalent row
in `src/db/tables/billing-trust.ts` keyed by matter, if the matter table
itself is core/foundation and off-limits to this engine — per
`src/engines/README.md`, foundation tables are read-only from an engine; the
actual column needs to land in whichever table currently owns matter status,
which this PR flags as an open question below rather than guessing at
foundation's schema). The refund/final-invoice records reuse the existing
invoice and ledger tables (c76/c79); no new table there either.

## Open questions for human review

1. **Where does `closeHoldReason` actually live?** `matters` is a shared
   foundation table this engine can read but not edit per README — someone
   with foundation-table authority needs to add this column (or confirm a
   billing-trust-owned side table keyed by matter is preferred instead).
2. Attorney sign-off on the refund-letter draft copy gate once it's
   written (new `copy.billing-trust.refund_letter` gate, pattern as c50).
3. Whether a zero-dollar close (nothing ever reached trust) should still
   require an explicit lawyer click-through, or can auto-clear — leaning
   toward requiring the click-through for audit-trail consistency, flagging
   for a product call.
